2. 경험 별 요약

뷰런 인턴

뷰런 인턴십에서 IoU 기반 평가 툴 개발을 맡았을 때, 요구사항에 없던 OpenGL 시각화를 직접 제안하고 구현했습니다. 이상치를 눈으로 바로 확인할 수 있어야 실질적인 도구가 된다고 판단했기 때문입니다. 이후 성과를 인정받아 LiDAR 데이터 전처리 병렬화까지 맡게 됐고, CUDA·OpenMP·OpenCL을 직접 학습해 최대 3배의 성능 향상을 만들었습니다.

glare rendering

학부연구생 시절 사수들이 수학적 어려움으로 방치해둔 Glare Rendering 최적화를 자원해서 맡았습니다. 베셀 함수, 여러 종 모양 함수들을 시도했지만 모두 막혔고, 수학 서적을 찾고 타 학과 친구들에게 조언을 구하며 접근을 계속 바꿨습니다. 결국 2D Gaussian 근사와 푸리에 급수를 결합한 알고리즘을 설계해, 렌더링 복잡도를 광원 수에 독립적인 구조로 전환했습니다.

CUDA Vector DB

고차원 대용량 데이터를 GPU로 처리하는 연구과제에서, 커널이 간헐적으로 실패하고 속도가 불안정한 문제를 마주했습니다. 입력 크기별 정답 일치 테스트를 먼저 만들고, 단계별 실행 시간을 분리 측정해 bank conflict가 원인임을 특정했습니다. 데이터 레이아웃을 조정하고 메모리 할당량을 디바이스 사양에 맞게 조절해 1차년도 성능 목표를 달성했습니다.

KingoM

6인 팀 프로젝트에서 시작 직후 팀 리더가 이탈하며 프로젝트가 중단될 위기가 생겼습니다. 제가 리더를 자원해 가장 먼저 소통 구조를 설계했습니다. When2Meet으로 공통 시간을 확보하고, Notion에 이슈를 기록해 누구든 흐름을 따라올 수 있게 했으며, 프론트-백엔드 간 JSON 형식과 로딩 정책을 사전에 합의해 통합 충돌을 최소화했습니다. 이탈자 없이 프로토타입을 완성했습니다.


**"팀원의 무임승차"** → 사실 확인 → 당사자와 1:1 대화 → 팀 전체 구조로 해결

팀 전체의 신뢰가 무너지기 전에 행동하는 것이 중요하다고 생각합니다. 저라면 먼저 무임승차처럼 보이는 원인이 무엇인지 사실부터 확인합니다. 개인 사정인지, 역할 분담이 불명확해서인지에 따라 접근이 달라지기 때문입니다. 이후 해당 팀원과 1:1로 이야기해 상황을 파악하고, 필요하다면 역할과 기여 범위를 팀 전체가 다시 합의하는 자리를 만들겠습니다. 불만을 제기하는 팀원들에게는 감정이 아닌 팀의 목표 기준으로 이야기할 수 있도록 방향을 잡아주겠습니다. KingoM 프로젝트에서 갈등이 생기기 전에 소통 구조를 먼저 설계했던 것처럼, 문제가 커지기 전에 구조로 해결하는 것이 팀 전체에 더 낫다고 생각합니다.

**"팀원이 잘못된 값을 넣어서 전체 데이터가 망가졌다"** → 책임 추궁보다 복구 우선 → 원인 파악 → 재발 방지 프로세스 제안

실수한 팀원을 추궁하기보다 팀 전체가 빠르게 복구에 집중하는 것이 먼저라고 생각합니다. 저라면 현재 데이터 상태를 파악해 복구 가능한 범위를 먼저 확인하고, 팀원들과 역할을 나눠 복구 작업을 병렬로 진행하겠습니다. 이후 실수한 팀원과 1:1로 원인을 파악하되, 개인 잘못이 아니라 프로세스의 문제로 접근합니다. 예를 들어 중요한 파라미터 변경 시 팀원 간 리뷰를 거치는 체크리스트를 만드는 것처럼, 같은 실수가 반복되지 않는 구조를 팀 전체가 함께 만드는 것이 더 중요하다고 생각합니다.

**"수개월 간 성과가 없고 팀원들이 변화를 두려워한다"** → 현재 상태를 데이터로 정리 → 작은 변화부터 제안 → Data Driven + Innovation

성과가 나지 않는 상황에서 변화를 두려워하는 건 자연스러운 반응이라고 생각합니다. 저라면 먼저 지금까지의 시도와 결과를 데이터로 정리해 팀원들과 공유합니다. 무엇이 막혀있는지를 감이 아닌 사실로 공유해야 다음 방향을 함께 결정할 수 있기 때문입니다. 이후 큰 변화보다 작은 단위로 시도할 수 있는 것부터 제안해 팀원들이 변화에 대한 부담을 낮출 수 있도록 하겠습니다. Glare Rendering 과제에서 막힐 때마다 접근 방법을 바꿔가며 결국 해결했던 것처럼, 방향을 바꾸는 것이 포기가 아니라 더 나은 선택임을 팀원들과 함께 확인하겠습니다.

**"팀에 막내가 들어왔는데 실수를 자주 한다"** → 실수를 지적보다 원인 파악 → 같이 스프린트 → KingoM에서 어려운 팀원 스터디룸 경험 활용

실수 자체보다 실수 후 낙담해 있는 상태가 더 걱정됩니다. 저라면 먼저 막내와 편하게 이야기할 수 있는 자리를 만들어 어떤 부분이 어려운지 파악합니다. 실수의 원인이 이해 부족인지, 환경이 낯선 것인지에 따라 도움 방식이 달라지기 때문입니다. KingoM 프로젝트에서 개발에 어려움을 겪는 팀원이 있을 때 스터디룸을 빌려 함께 스프린트를 진행했던 것처럼, 옆에서 같이 해결하는 시간을 만들겠습니다. 실수를 지적하기보다 다음에 어떻게 하면 되는지를 함께 정리해주는 것이 더 빠르게 성장하는 방법이라고 생각합니다.
