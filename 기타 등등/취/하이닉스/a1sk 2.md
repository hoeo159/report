- MSA와 Monolithic 아키텍처의 차이를 설명하고, MSA의 장단점을 말씀해주세요.

어떤 애플리케이션을 만드는 과정에서 Monolithic은 하나의 중심 서비스로 만드는 하나의 애플리케이션, MSA는 micro service app으로 여러 작은 서비스를 모아 하나의 애플리케이션을 만드는 것입니다. Monolithic은 기능 간 의존성이 높고 스파게티 코드를 만들 가능성이 높다. 또한 작은 오류가 전체의 오류로 번지기 쉽다. MSA의 경우 각 기능들이 컴포넌트로 조립되어 있기 때문에 추후에 새로운 서비스를 넣거나 오류에 대응하기 쉽다는 장점이 있다. 하지만 MSA의 경우 다른 기능을 호출할 때 요구하는 자원이 더 크고 구조를 관리해주어야 하기 때문에 개발 시간이나 난이도가 증가한다는 단점이 있습니다.

모노는 메소드 호출 같은 방식인데 MSA는 네트워크 통신 같은 오버헤드가 더 크다. 여러 시스템이나 대규모 환경에서는 각 서비스가 독립적으로 배포, 운영 추후에 디벨롭 하기도 용이하기 때문에 유리하다.

- Redis가 무엇인지 설명하고, 어떤 상황에서 사용하면 효과적인지 말씀해주세요.

비정형 데이터를 저장하기 위한 key value 기반의 비관계형 database management system입니다. 가장 큰 특징은 RAM과 같은 인메모리 데이터 구조이며, 당연히 read, write 속도가 디스크 보다 훨씬 빠르다는 장점이 있다. 같은 요청이 여러 번 들어올 경우, 캐시 수준에서 저장된 결과 값을 반환하기 때문에 DB의 오버헤드를 줄이고 서비스의 속도도 느려지지 않는다. 하이닉스에서도 제조 시스템이나 실시간 데이터 처리에서 자주 조회되는 공정 데이터를 캐싱해서 활용할 수 있다. 비정형 데이터를 관리하기 때문에 IoT 센서 데이터, 공정 로그 등 다양한 형태의 데이터를 다룰 때 적합하다. 하지만 인메모리 데이터 이기 때문에 서버 장애에 대한 대비가 필요하다.

예를 들면 RDB 스냅샷(특정 간격마다 메모리에 있는 redis data를 전체를 디스크에)이나 AOF, append only file(wirte, update 명령 실행 마다 연산 자체를 로그 파일에 기록)로 디스크에 주기적으로 백업하는 방식이 있다.

- REST API와 GraphQL의 차이를 설명해주세요.

우선 둘의 공통점은 클라-서버 모델에서 서로 다른 서비스나 앱 간 데이터를 주고받는 API 아키텍쳐 입니다. 하지만 REST API는 소통을 위한 GET, PUT 등의 HTTP 메서드, 고정된 구조를 따른 리소스 이동이 일어납니다. 반면 정해진 형식을 통한 쿼리를 이용해 리소스를 관리합니다. REST API는 GET /user/id 같은 메서드와 URL로 된 리소스로 행동을 정의합니다. 데이터 요청을 하면 서버가 정해진 구조로 반환합니다. 만약 유저 이름과 주문 정보가 필요하다면 API를 두 번 호출해야합니다. 그래서 이름만 필요한데 관련 전체 데이터가 다오는 문제 같은 문제점도 있다.

반면 GraphQL은 쿼리를 통해 클라이언트가 원하는 것만 요청할 수 있습니다. 유저 이름과 주문 정보도 한 번에, 필요한 것만 받을 수 있습니다. 그에 따라 쿼리 대한 복잡도 관리가 필요합니다. REST API는 리소스가 잘 정의된 데이터에 적합하며, GraphQL은 크고 복잡하며 서로 연관되어 있는 데이터 구조에 적합합니다. 

- Spring Boot가 무엇인지, 그리고 일반 Spring과 어떤 차이가 있는지 설명해주세요.

간단하게 말하면 spring boot는 spring을 더 빠르고 쉽게 쓸 수 있게 자동화 한 것입니다. spring과 spring boot는 모두 spring framework 기반입니다. spring framework는 java 기반 애플리케이션 개발을 위한 프레임워크입니다. spring은 이러한 spring framework의 핵심 모듈을 모아서 만든 framework입니다. 개발자가 직접 스프링 컨테이너를 구상하고, 필요한 객체를 등록하고 의존성을 설정해야 합니다. spring boot는 프로젝트의 설정과 라이브러리 의존성을 자동으로 처리하고 실행 가능한 jar 파일을 만들 수 있습니다. 따라서 spring은 세밀하고 정교한 작업이 가능하지만 복잡하고 spring boot는 의존성을 한 번에 관리할 수 있는 등 설정을 최소화하고 빠르게 앱을 만들 수 있습니다.

- RAG가 무엇인지 설명하고 일반 LLM API만 사용하는 것과 어떤 차이가 있는지 말씀해주세요.

RAG, 검색 증강 생성은 LLM의 보편적인 문제점을 해결하기 위한 접근 방식입니다. LLM의 문제점들은 답이 없을 때 허위 정보를 생성하는 할루시네이션 현상, 구체적이고 최신의 정보보다 보다 오래되고 일반적인 정보 제공, 신뢰할 수 없는 출처 등 있습니다. LLM은 사용자 입력을 바탕으로 훈련된 정보나 사전에 정의된 정보를 바탕으로 응답을 생성합니다. RAG는 외부 데이터를 검색해서 LLM에 컨텍스트로 제공합니다. 외부 데이터는 기존의 텍스트 기반 데이터 뿐만 아니라 그림, 음성, 영상 같은 비정형 데이터도 벡터 임베딩되어 저장됩니다. 약간 지식 라이브러리 같은 느낌입니다. 이때 사용자 입력 역시 벡터 임베딩된 같은 동작으로 벡터화 되고 유사도 기반을 통해 라이브러리에서 정보를 꺼낼 수 있습니다. 이를 통해 신뢰할 수 있는 지식에 관해 검색하고, 생성된 텍스트 출력을 더 잘 제어할 수 있습니다.(내가 예전에 쓴 pinecone vdb도 연관해서 소개?? 이게 RAG인가?)

- ETL과 ELT

둘 다 분석을 위한 데이터를 준비하는 일련의 프로세스입니다. 프로세스의 진행 과정에서 두 프로세스의 차이점이 있습니다. ETL은 크게 다양한 소스에서 데이터를 추출하고 데이터베이스의 구조에 맞게 전환합니다. 그 뒤 데이터베이스에 적재합니다. ELT는 데이터를 추출, 데이터 웨어하우스에 저장합니다. 웨어하우스는 적재가 아닌 분석을 위한 저장소입니다. 그 뒤 데이터 웨어하우스 내에서 전환 및 보강이 이루어집니다. ETL은 구조에 맞게 전환 후 적재를 하기 때문에 테이블 구조 같은 정형 데이터에 적합한 반면 ELT는 비정형 데이터를 포함한 다양한 형식을 처리할 수 있습니다. 처리 성능이 좋은 환경에서는 적재 후 변환이 빠르고 모든 전환이 웨어하우스 내에 이루어 지기 때문에 ETL보다 필요한 시스템 수가 적다.

- 데이터 인덱싱

데이터 인덱싱은 데이터베이스에서 검색의 속도를 높여주는 역할을 합니다. 마치 단어 사전에서 단어를 찾을 때 처음부터 살피는 게 아닌 목차를 이용해 A~Z까지 위치로 이동한 후 검색하는 것처럼 tree로 이루어진 자료구조 속에 데이터를 저장하여 반대 리프 노드의 search 비용을 없앨 수 있는 효과를 기대할 수 있습니다. 특히 데이터 베이스에서는 B+ tree라는 데이터 베이스 알고리즘이 있습니다. 모든 데이터를 리프 노드에 저장하고 리프 노드끼리 연결되어 있어 범위 검색에 유리한 구조입니다. 하지만 이러한 구조 때문에 인덱싱을 위한 추가적인 저장 공간이 필요합니다. 또한 높은 검색, 조회 성능에 비해 insert, update, delete 연산에 추가적인 작업이 필요하다. 과도한 인덱싱은 오히려 성능을 떨어뜨리기 때문에 인덱싱을 위한 설계가 필수적이다.

- 컨테이너와 VM

두 기술 모두 가상화라는 공통점이 있습니다. 여기서 말하는 가상화는 하드웨어 위에 추상적인 계층을 만들어서 소프트웨어를 동작하게 하는 방식입니다. VM은 하나의 물리적인 서버, 호스트 위에 여러 개의 독립된 운영체제를 통째로 올리는 기술입니다. 호스트 OS와 여러 개의 VM OS 사이를 하이퍼바이저라는 가상화 소프트웨어를 통해 관리합니다. 컨테이너는 호스트 OS 위에서 가상화를 진행합니다. 따라서 모든 컨테이너는 호스트 OS의 커널을 공유해서 사용합니다. 반대로 VM은 호스트 OS의 커널이 아닌 각 VM의 커널을 가집니다. (여기서 커널에 대한 간단한 정의를 하는 것도 좋을 듯) 때문에 VM은 무겁고 느리고 하드웨어 자원을 쓸 때 하이퍼 바이저를 거치기 때문에 일부 손실이 발생합니다. 반면 컨테이너는 컨테이너 이미지 상에 애플리케이션과 라이브러리만 있기 때문에 작고 빠릅니다. 하지만 호스트 OS의 커널을 공유하기 때문에 예를 들어 윈도우 호스트 상에 리눅스 컨테이너를 직접 실행하는 것에 제약이 있습니다.

- CI/CD

지속적 통합과 배포를 의미, CI는 코드 변경 사항을 정기적으로 빌드하고 테스트하고 공유 레포에 병합하는 과정을 나타냅니다. CD는 공유 레포로 자동으로 Release하는 것, production 레벨 까지 deploy 하는 것을 말합니다. CI는 다수의 개발자가 Git과 같은 툴을 공유하며 사용하는 환경에서 자동화된 빌드, 테스트를 통해 기존 소스코드와의 충돌 등을 방어하는 장점이 있습니다. 특히 작은 기능 별로 서비스를 쪼개고 Agile로 개발하는 MSA 환경에서 중요합니다. CD는 이러한 레포를 넘어 고객에게 전달되는 production 환경까지 릴리즈 되는 것을 의미합니다. 이러한 CI/CD 파이프라인은 SK하이닉스 IT 환경처럼 여러 팀이 동시에 개발하고 빠르게 배포해야 하는 MSA 기반 시스템에서 특히 중요합니다. 코드 품질을 자동으로 검증하고 배포 주기를 단축해 현장의 요구에 빠르게 대응할 수 있기 때문입니다.
